What is a fixture?

A fixture is a reusable mechanism used to prepare the test environment before a test and optionally clean it up afterward.

A good interview answer is:

"I select fixture scope based on resource lifecycle and test isolation. 
I use function scope when every test requires an independent resource, module or class scope when the resource can safely be reused, 
and session scope for expensive resources such as global configuration or environment-level initialization."


************************************************************************************************************************************************

 Why we use yield instead of return in fixtures:-

     In pytest fixtures, we use yield (instead of just return) when we need to perform both setup and teardown around a test. 
     Think of yield fixtures as a context manager for tests: everything before yield is setup; everything after yield is teardown.

    return in a fixture → provides a value to the test (setup only).
    yield in a fixture → provides a value and runs teardown code after the test finishes (setup + cleanup).
    Pytest guarantees the teardown runs even if the test fails, errors, or raises exceptions.

Use autouse fixtures for genuinely common behavior, not for every reusable setup operation.

"An autouse fixture is a fixture configured with autouse=True, which Pytest automatically applies to all applicable tests within its scope without explicit fixture injection. 
I use autouse fixtures for common cross-cutting setup or cleanup activities such as environment validation, logging, or collecting diagnostics. 
I avoid using autouse for business-specific setup because explicit fixture dependencies make tests easier to understand and maintain."

What is conftest.py?

conftest.py is a special Pytest configuration file used primarily to define shared fixtures, hooks, and test configuration for a directory hierarchy.

************************************************************************************************************************************************

Important correction: "Global fixture"

People often say:

"Global fixture"

But Pytest doesn't have a special fixture scope literally called global.

Instead, a fixture in the root-level conftest.py can be available throughout the relevant test directory hierarchy.

So in interviews, it is better to say:

"A root-level conftest.py provides shared fixtures across the test suite's directory hierarchy."

rather than claiming there is a global fixture scope.

⭐ Interview Questions You Should Be Ready For

For these concepts, I would expect questions such as:

1. What is an autouse fixture?

A fixture configured with autouse=True that Pytest automatically executes for applicable tests without explicit fixture injection.

2. Should every fixture be autouse?

No. I use autouse for genuinely common cross-cutting setup or cleanup. For business-specific dependencies, explicit fixture injection is preferable because it makes dependencies visible.

3. What is conftest.py?

A special Pytest file used to define shared fixtures, hooks, and configuration within a directory hierarchy without requiring explicit imports.

4. Can we have multiple conftest.py files?

Yes. Fixtures can be organized at different directory levels, and their availability follows the directory hierarchy.

5. Is smoke a built-in Pytest marker?

No. smoke and regression are typically custom markers. Built-in markers include skip, skipif, xfail, and parametrize.

6. Why register custom markers?

To tell Pytest about custom markers, avoid unknown-marker warnings, document their purpose, and maintain consistent test execution.

7. How do you execute only smoke tests?
pytest -m smoke
8. How do you execute regression tests?
pytest -m regression
9. How do you run the same test with multiple datasets?
@pytest.mark.parametrize(
    "username",
    ["admin", "operator", "readonly"]
)
def test_login(username):
    ...
10. Difference between fixture parameterization and pytest.mark.parametrize?

Fixture parameterization is primarily useful for varying setup/resources, while pytest.mark.parametrize is primarily used for varying test inputs and expected results.

⭐ Interview-ready answers

Q1. Why do you use logging in automation?

"I use logging to capture meaningful execution information and simplify failure analysis. 
In my Nutanix automation framework, I log important UI actions, API requests and responses, test data references, Kubernetes/service checks, and failure details. 
This is especially useful when tests execute through Jenkins because I can analyze the execution history without reproducing the issue locally."


Q2. What logging levels do you know?

"The commonly used levels are DEBUG, INFO, WARNING, ERROR, and CRITICAL. I use DEBUG for detailed troubleshooting information, 
INFO for normal execution flow, WARNING for unexpected but recoverable conditions, ERROR for operation failures, and CRITICAL for severe failures that can prevent further execution."


Q3. What is pytest-xdist?

"pytest-xdist is a Pytest plugin that enables parallel and distributed test execution. I can use pytest -n 4 to execute tests across four workers. 
This can significantly reduce execution time for large regression suites, provided the tests and test data are properly isolated and parallel-safe."


Q4. What is pytest-cov?

"pytest-cov integrates coverage measurement with Pytest. It helps identify which parts of the Python code under test are being exercised. 
However, I don't treat coverage percentage as a direct measure of test quality because high coverage doesn't necessarily mean all business scenarios are validated."


Q5. What is pytest-html?

"pytest-html is a plugin that generates HTML test execution reports. It provides a lightweight way to view test status, failures, and execution details. In my framework, I primarily worked with Allure for richer reporting, but pytest-html is useful for simpler HTML reporting requirements."


Q6. What is a flaky test?

"A flaky test is a test that produces inconsistent results without a corresponding change in the application or test logic. Common causes include synchronization problems, unstable environments, shared test data, network issues, and improper cleanup."


Q7. How do you handle flaky tests?

A strong SDET answer:

"First, I don't immediately add retries. I analyze the failure using logs, screenshots, API responses, stack traces, and environment information to identify the root cause. For Selenium failures, I check synchronization and use explicit waits instead of hard sleeps. For API or Kubernetes-related failures, I check network conditions, service availability, pod state, and response behavior. If the failure is genuinely transient, I can use a controlled retry mechanism such as pytest-rerunfailures as a temporary mitigation, while still tracking and fixing the underlying root cause."

That is much stronger than simply saying:

"I use rerunfailures."

Pytest Hooks — 🔥 High-Value SDET Topic

Pytest hooks are predefined extension points that allow us to customize or control Pytest's execution lifecycle.

In simple terms:

Fixtures are mainly used to provide test dependencies/setup/teardown, while hooks allow us to customize what Pytest itself does at different stages of test execution.

What exactly is a hook?

A Pytest hook is a special function with a predefined name that Pytest automatically calls at a specific point in its execution lifecycle.

For Example:-

def pytest_sessionstart(session):
    print("Pytest session started")

Fixture
   ↓
"What does my test need?"

Hook
   ↓
"What should Pytest do at this point in its lifecycle?"


"Pytest hooks are predefined extension points provided by Pytest that allow us to customize the test execution lifecycle. 
I generally define them in conftest.py or plugins. For example, pytest_sessionstart can be used for session-level framework initialization, 
pytest_runtest_setup can be used for test-level preconditions or framework-level logging, and pytest_runtest_call is associated with the actual test execution phase.

In an automation framework, I use hooks mainly for framework-level concerns rather than replacing fixtures. 
For example, fixtures handle resources such as Selenium drivers, API clients, authentication, and test data, while hooks can handle things like execution metadata, 
environment initialization, failure diagnostics, and reporting. For capturing screenshots or logs when a test fails, pytest_runtest_makereport is particularly useful."
